Два файла, собранные из репозитория [android9009/My-luas](https://github.com/android9009/My-luas):

## Что именно делает каждая кнопка

### `skeet_all_patches.lua` — контейнер `LUA → Patches`

| Элемент | Действие |
| --- | --- |
| `Normalize patch (Z_NORM)` | 7 байт по `0x1062A526` → `90` (затирание нормалей) |
| `Direction flags patch` | 3 байта по `0x106E3F9C` → `90` |
| `Shoot like Skala Johnson` | `0x106D67A8` ← `B8 01 00 00 00 C2 08 00` (`mov eax,1 ; ret 8`) |
| `Анимация меню (fade / spin)` | память не патчится: двигает размер/позицию меню в `paint_ui` и прячет иконки табов |
| `*: адрес` | переопределение адреса сайта в hex (`0x1062A526` или `1062A526`); пусто = встроенный |
| `Read sites (проверить адреса)` | печатает текущие байты каждого сайта (включая все panchan-сайты) и их пригодность — **сначала жми это** |
| `Restore everything` | снимает все патчи, включая panchan, и возвращает поля меню |

#### panchan: `Патчи panchan (airlag + ragebot improved)`

| Элемент | Действие |
| --- | --- |
| `panchan base (hex, пусто = 0x43320000)` | все 19 сайтов считаются от одной базы; при переезде модуля меняется здесь |
| `panchan: Air lag` | 6 байт @`+0x08C17C` → `90` |

| Элемент | Действие |
| --- | --- |
| `Backtrack Patch` | расширяет окно бэктрака (immediate в lagcomp-проверке), поднимает `sv_maxunlag` |
| `Window` | 1…16 тиков (сток 8) |
| `Aggressive` | доп. три патча: не чистить записи, без экстраполяции, записи валидны на fakeduck |
| `Revert now` / `Panic revert` / `Diagnose` | снять всё / хоткей-паника / база и байты всех сайтов |
| `Preserve valid records` | `0F` → `00` в `jne` скана записей: условный переход превращается в «на месте», запись не отбрасывается |
| `Early defensive activation` | `dec edi` → `NOP`: defensive включается на тик раньше |
| `Skip break distance check` | два вызова `lagrecord_within_break_distance` → `B0 00 90 90 90` |
| `Defensive on backtrack` | `disp32` у `jz` → свой стаб (`mov byte [esi+0x1A],1 ; jmp назад`), стаб освобождается при снятии |
| `Extrapolation primary` | `call should_extrapolate` → `jmp` на свой стаб: `breaklc == 0 && hittable != 0` → сразу `mov eax,1`; иначе настоящий `call` и `jmp` назад. По умолчанию **выключено** |
| `Custom record selection` | сайт `select_lagrecord` (39 байт) → `jmp` в пещеру: выбор записи по `simulation_time`, ветки `0x527`/`0x7E2`, `animfix` `thirdperson_recoil` (пещера 3) |
| `Custom fallback selection` | патч `fb_sig` (6 байт) → вторая пещера fallback-выбора записи + стаб `GetEntityIndex` |
| `Model hook (persistence)` | 5 байт `83 EC 54 53 56` по `studiorender.dll+0x536A6` → пещера: подмена цвета модели `[ecx+0x240..0x24C]` и копирование матриц через вторую пещеру. По умолчанию **выключено** |
| `studiorender RVA (hex)` | RVA функции отрисовки (по умолчанию `0x536A6`); перед установкой сверяется пролог `83 EC 54 53 56` |
| `Read sites` (в этой группе) | печатает найденные адреса всех четырёх шаблонов viera |

#### Группа `Rage → NL Rage Fixes` (раздел 9.8)

| Элемент | Действие |
| --- | --- |
| `Rage native fixes (neverlose.dll)` | пять байтовых патчей из `persistence.lua` (`patches[1..6]`): `F3 0F 5B C0 0F 5B C0` ×2 → `90`×7 (срок записи в builder/iterator), `F3 0F 59 0D <disp32>` → `90`×8 (множители слоя 0.75 и 1.25), `F3 0F 10 0D <disp32>` → `90`×8 (вес слоя 1.0) |
| `Read rage sites` | база `neverlose.dll` и по каждому шаблону: адрес и живые байты либо причина отказа |

Набор применяется целиком или никак; сверяются байты опкода до записи и после
неё (disp32 у `F3 0F 59 0D`/`F3 0F 10 0D` свой на каждой сборке, поэтому
сверяется только опкод). Неоднозначный шаблон (два совпадения) — отказ, а не
«патчим первое, что нашли».

#### Группа `Rage → NL Hooks (persistence)` (раздел 9.9)

| Элемент | Действие |
| --- | --- |
| `cl_move hook (engine.dll)` | в шаблоне `8A CB F2 0F 10 05 … F3 0F 10 45 FC E8` на `+31` стоит `call rel32`; переписывается **только disp32** (`E8` остаётся), вызов уходит в пещеру 64 Б: `sub esp,4 / movss [esp],xmm0 / pushfd / pushad / mov eax,колбэк / call eax / test eax,eax / jne ret / jmp настоящая цель / ret` |
| `cl_move callback (hex)` | адрес нативного колбэка; без него хук не ставится |
| `write_usercmd hook (VClient018+24)` | хук vtable-слота 24 интерфейса `VClient018`: пещера 32 Б (`push ebp / mov ebp,esp / mov ecx,[ebp+8] / mov edx,[ebp+0C] / push [ebp+10] / mov eax,колбэк / call eax / add esp,4 / pop ebp / ret`) записывается в слот |
| `write_usercmd callback (hex)` | адрес нативного колбэка; без него хук не ставится |

Байты пещер совпадают с `emit_cl_move_stub` / `emit_write_stub` из
`persistence.lua`, включая `rel8 = 5` у ветки «колбэк всё сделал» и `rel32` на
настоящую цель `cl_move`. Перед установкой проверяются: PE-подпись модуля,
единственность шаблона, исполняемость места вызова, `E8` на месте вызова,
читаемость слота vtable и его непустота; после записи — обратное чтение,
при снятии возвращаются disp32 и слот, пещеры освобождаются.

Честное ограничение: в оригинале колбэк — это `bind_function` от Lua-функции,
то есть нативный код, который создаёт только рантайм persistence. Поэтому
колбэк задаётся адресом, а не «включается галочкой»: без адреса хук честно
отказывается и пишет причину.

Сайты viera **не** заданы числами: они находятся сканом байтов по образу чита
(`jne`-скан, `dec edi`, два вызова break distance, гейт defensive). Не нашлось —
патч отказывается и пишет причину.

Пещеры viera (раздел 9.6) собраны из тех же байтов, что в оригинале: одно
`VirtualAlloc` на 4096 байт `PAGE_EXECUTE_READWRITE`, внутри — `cave1` (+0x000,
главный путь), `cave3` (+0x16A, animfix), стаб entindex (+0x272), `cave2`
(+0x290, fallback). Абсолютные адреса (`g_cmd_ctx`, `g_entindex`,
`g_is_firing`, `g_tpr_arr`, смещение `m_flThirdpersonRecoil`, адреса возврата)
считаются от найденных сайтов и от `utils.get_netvar_offset`, а не зашиты
числами; при снятии байты возвращаются, пещера освобождается.

Про `model hook` (раздел 9.7) — без прикрас: пещера срабатывает только тогда,
когда управляющий блок заполнен **тем же** thread id и **тем же** указателем
модели, с которыми оригинал вызывал отрисовку. Его draw pass — это движок
отрисовки на 176k строк, он не переносится. Поэтому по умолчанию хук выключен,
а блок можно заполнять самому: `NL_PERSISTENCE_MODEL:activate(model_ptr,
call_ptr)`, `:set_color(r,g,b,a)`, `:set_capture(buffer, size)`, `:captured()`,
`:skip_color(bool)`, `:deactivate()`. Если блок не заполнен — пещера просто
воспроизводит оригинальный пролог и уходит назад, ничего не меняя.

## Что переделано относительно исходников

Это не «переписал красивее», а конкретные исправления:

1. **Не падает на загрузке.** Оригинальные skeet-патчи делали
   `client.find_signature(...) or error("errN")` на верхнем уровне: если
   сигнатура не нашлась, скрипт не загружался с ошибкой. Здесь всё
   резолвится один раз, под `pcall`, а при неудаче скрипт пишет причину в
   консоль и **не трогает память**.
2. **Один резолв Win32 на весь скрипт.** Сначала `ffi.load("kernel32")`, если
   чит это запрещает — тот же signature-гейт (`push ecx; ret` + адреса из IAT),
   что и в оригинале. Оригиналы делали это в каждом файле заново.
3. **Проверка адреса перед записью.** `VirtualQuery`: регион закоммичен,
   исполняемый, не `PAGE_GUARD`/`PAGE_NOACCESS`. Адрес из другого билда просто
   не пройдёт проверку — вместо того чтобы занопать случайные байты.
4. **Отказ на padding.** Если по адресу сплошные `0xCC`/`0x90` — это padding
   чужого билда, патч не применяется, в логе написано почему.
5. **Возврат старой защиты страницы.** Оригиналы после записи ставили
   `PAGE_EXECUTE_READ` безусловно; здесь возвращается то значение, которое
   вернул сам `VirtualProtect`.
6. **Проверка записи обратным чтением** и снапшот оригинала до записи; повторное
   включение идемпотентно, выключение возвращает байты байт в байт.
7. **Переопределение адресов из меню** (skeet) — при обновлении чита адреса
   меняются, скрипт остаётся тем же. Для panchan переопределяется база целиком.
8. **Анимация меню под защитой.** Поля меню читаются и проверяются на
   правдоподобность ДО первой записи (размеры, позиции, режим, `0..1`,
   указатели табов). Не похоже на меню — патч не включается и говорит об этом.
   Кадр обёрнут в `pcall`: ошибка выключает патч и возвращает поля, а не
   ломает меню каждый кадр.
9. **NL: причины отказа вместо молчания.** `Patch:arm` возвращает причину,
   первый неудачный arm и итоговая сдача после 8 попыток пишутся в консоль;
   частичный arm откатывается целиком.
10. **NL: `sv_maxunlag` под защитой.** Поднимается только вверх, ровно на окно
    + вашу исходящую задержку, и возвращается только если там всё ещё **наше**
    значение. Если cvar недоступен — окно работает, запаса не будет (сказано
    в консоли).
11. **panchan: эталон байтов у каждого сайта.** В panchan половина патчей
    проверяет только опкод, а операнд пишет любой. Здесь сверяется ещё и
    **исходное значение операнда** (константа `0x43472B60`, `0x4346FC50`,
    `0x80`, `0x64`, `0x13`, `0xCA`): если по адресу другой билд — отказ, а не
    «повесим рандомную константу». Своё уже записанное значение тоже считается
    валидным, поэтому слайдеры можно двигать сколько угодно.
12. **panchan: группа применяется целиком или никак.** Один неподошедший сайт
    откатывает уже записанные сайты этой группы: рейджбот не остаётся
    наполовину пропатченным. Отказ печатается один раз, а не каждый кадр.
13. **panchan: без повторной записи на каждом кадре.** `Site:apply` сравнивает
    живые байты с желаемыми и пишет только при отличии (оригинал делал запись
    каждый тик, пока включена галочка).
14. **viera: сайты ищутся сканом, а не числами.** Шаблоны с джокерами, образ
    чита читается кусками по 256 КБ (буфер освобождается, как только все
    шаблоны найдены). Первое совпадение берётся, но если шаблон встречается
    несколько раз — это печатается в консоль.
15. **viera: стаб defensive живёт ровно столько, сколько патч.** `VirtualAlloc`
    перед записью, `VirtualFree` при снятии/отказе/ошибке проверки байтов;
    `FlushInstructionCache` после записи стаба.

остались две вещи; они перечислены здесь, чтобы это не выглядело как

| --- | --- | --- |
| `prediction_*` (vtable `VClientPrediction001` +3/+8/+19) | `74002…74034`, установка `88774…` | стаб 40 байт, сверяет адрес возврата и зовёт нативный колбэк |

сопоставить релокации и написать такой же тест, как для `model hook`, поэтому
они идут отдельными шагами, а не «заодно».

## Адреса — не универсальные

`0x1062A526`, `0x106E3F9C`, `0x106D67A8`, блок `0x4347xxxx` (skeet),
`0x43320000…` (panchan) и `0x41400bf0…` (NL) сняты с конкретных билдов.
Скрипты это не скрывают:

* skeet: `Read sites` печатает байты и вердикт по каждому сайту (включая все
  panchan-сайты); адрес можно ввести руками в поле; для анимации меню
  переопределяется база модуля, для panchan — отдельная база.
* panchan: его сайты заданы абсолютными VA, поэтому у каждого есть эталон
  байтов и проверка операнда — на чужом билде патч откажется, а не запишет.
* NL: `Diagnose` печатает базу и байты всех сайтов; база ищется сама
  (приватный исполняемый регион + `GetModuleHandleA`), поэтому переезд модуля
  на другой адрес её не ломает — это проверено тестом на двух разных базах.
  Сайты viera вообще не зависят от базы: они находятся сканом.

Если сайт не подходит — скрипт откажется и объяснит, а не запишет «наугад».

## Тесты без чита

Оба скрипта реально исполняются против фейкового чита: симулированная память,
регионы, `VirtualQuery`/`VirtualProtect`/`VirtualAlloc`/`VirtualFree`,
поиск сигнатур по байтам, меню, события и `entity`. Проверяются
включение/выключение, возврат байтов, отказы, анимация меню, паник-хоткей,
`sv_maxunlag`, группы panchan (включая проверку операнда, откат группы и
поведение Jump Scout по прицелу), скан шаблонов viera, стаб defensive и работа
на другой базе модуля, пещеры выбора записи и экстраполяции (байты пещер,
релокации, возврат), а для model hook из persistence — байты обеих пещер и все
18 релокаций, пролог, `call` в пещеру 2, управляющий блок (thread id, цвет,
буфер костей, счётчик), идемпотентность по тикам, отказы (нет модуля, чужой
пролог, не PE-образ, кривой RVA) и возврат байт в байт с `VirtualFree`.

```
pip install --break-system-packages lupa
python3 tests/lua/run.py
```

Ожидаемый вывод — `TOTAL 333 passed, 0 failed`.

Чего эти тесты **не** доказывают: что конкретный билд чита совпадает с
адресами (это проверяет `Read sites` / `Diagnose` уже в игре) и что патч
визуально делает то, что задумано — это ручная проверка.
